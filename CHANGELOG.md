# Changelog

All notable changes to Codeveira are documented here.

## [Unreleased]

### Security

- **`app` and `lsp` no longer publish their ports directly to the host — only the bundled `nginx` container does.** Previously `app:3000` and `lsp:7777` were published to the host *in addition to* nginx's `443`/`80`, so anyone could reach either one directly in plain HTTP/TCP, bypassing nginx and TLS entirely regardless of Domain & HTTPS configuration — `FORCE_SSL=true` didn't fully close this, since the first request (session cookie, login password) still traveled in cleartext before any redirect could fire. **Action required if you run your own external reverse proxy instead of the bundled nginx** ("Bring your own reverse proxy" in the README): merge the new `docker-compose.byo-proxy.yml` (`docker compose -f docker-compose.yml -f docker-compose.byo-proxy.yml up -d`) to republish those two ports, and comment out the bundled nginx's own `ports:` block by hand (Compose can't subtract it via an override). Everyone using the bundled nginx (the default, recommended setup) needs no action — `docker compose up -d` already only publishes 80/443/7777 from nginx now.
- **Repository access control (IDOR) fix** — `Browse`, `Reviews`, `Comments` (including posting new comments), `Labels`, `Commits`, and the repository overview/README/metrics/analytics pages now correctly scope repository lookups to repos the current user is a member of (or all repos for global admins). Previously any logged-in user could view — and in some cases modify — data belonging to a repository they weren't a member of, just by changing the numeric `repository_id` in the URL. The REST API and MCP server were already scoped correctly and are unaffected.
- **Azure DevOps and Gerrit webhooks now require authentication.** These platforms don't support HMAC payload signing the way GitLab/GitHub/Gitea/Bitbucket do, so requests are now authenticated via HTTP Basic Auth instead — set `AZURE_WEBHOOK_SECRET`/`GERRIT_WEBHOOK_SECRET` and configure the matching password on the webhook subscription/plugin config. **Action required on upgrade:** these webhooks will start rejecting requests with `401` until the new env vars are set and the receiving side is configured to send Basic Auth.
- **Encryption at rest for Repository access tokens, AI provider API keys, user API tokens, and sensitive settings** (CI webhook token, SMS API token, etc.) via Rails Active Record Encryption. **Action required on upgrade:** set `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`, `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY`, and `ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT` in `.env` before starting — the app won't boot without them. Existing values are re-encrypted automatically the next time `rails db:migrate` runs; nothing is lost or requires manual re-entry.
- **SSRF protection** for the repository instance URL (self-hosted GitLab/Gitea/Forgejo/Bitbucket Server/Azure DevOps/Gerrit), outgoing webhook URLs, and the AI reviewer's custom API URL — blocks cloud metadata endpoints and the app's own internal service names, while still allowing arbitrary internal hostnames and private IP ranges (required for these self-hosted/internal-network features to keep working).
- **Account lockout** — 10 failed login attempts locks an account for 1 hour, closing off online brute-force against `/users/sign_in`. Minimum password length raised from 6 to 8 characters.
- **`FORCE_SSL` option** — set `FORCE_SSL=true` once TLS is terminated in front of the app to redirect HTTP→HTTPS and mark session cookies `Secure`.
- **Backup upload hardening** — uploaded `.dump` files are now checked against a maximum size (`MAX_BACKUP_UPLOAD_SIZE`, default 2GB) and a valid pg_dump custom-format signature before being accepted for restore.
- **Non-root containers** — `app`, `sidekiq`, `indexer`, and `lsp` now run their application process as a non-root user rather than root, reducing the impact of any future RCE in a dependency.
- **Upsource import SSRF check now enforced per-request**, not just once when the URL is first entered — closes a DNS-rebinding window during the (potentially long-running, re-runnable) import job.

### Added
- **Teams — cross-repository user groups with a lead/member rollup view** (Standard) — closes a real data-model gap flagged twice in planning (CODEOWNERS-style reviewer routing, and again on its own): previously `User`/`RepositoryMember` only supported per-individual, per-repository scoping, with no way to ask "what does my team own that's stuck, across every repo it touches." New `Team` (name, description) has-many-through `TeamMembership` (member/lead role) to `User`, modeled directly on the existing `Repository`/`RepositoryMember` pattern. Admins manage teams and membership under **Settings → Teams** (one member added/re-roled/removed per request, same pattern `RepositoryMembersController` already uses, not a wholesale-replace form — every change is audit-logged). Any team member or lead — no admin access required — gets a `/teams/:id` rollup via a new top-nav **Teams** link: open/stale/needs-response reviews and pending assignments across every member's repositories, plus per-member stats (authored, approvals, comments, last active), extending the existing dashboard and per-user-stats query shapes from a single user to an array of team member IDs. A global admin can open any team's rollup without being a member. License-gated at Standard (`teams`).
- **Pull Request Mode — opt-in live PR/MR review, alongside post-commit** (Extended) — a second, per-repository review lifecycle that runs concurrently with the existing post-commit flow (which is completely unchanged and stays the default); a repository picks either, both, or neither. Scoped to **GitLab and GitHub** for this pass. Reuses `Review`/`Commit` rather than forking into parallel models — a new `review_kind` column (`post_commit`/`pull_request`, default `post_commit` so every existing row is untouched) plus `pr_target_branch`/`pr_head_sha`/`mergeable`/`merged`/`merged_at`, and `source_id` (already used by Upsource import as a generic external-review dedup key) reused as `"<platform>:<repo>#<iid/number>"`. Enable per repository via **Edit → Pull Request Mode** (GitLab/GitHub only), then turn on "Merge request events"/"Pull requests" on that repository's existing webhook — no new webhook URL. New `ProcessPullRequestJob`, fully separate from and never calling into `ProcessPushJob`, handles open/reopen (creates the review and its first commit via the existing `fetch_compare_diff`), synchronize/update (incremental diff as a new `Commit`, redelivery-safe via a `pr_head_sha` check), and close/merge. Symbol indexing, ownership stats, and semantic analysis intentionally fire once, at merge (against the branch the PR actually landed on) rather than on every open/sync — indexing a PR's mutable, force-pushable source branch repeatedly would leave stale entries behind. A new **Merge** button on the review page (`pull_request?` reviews only, gated on every reviewer having approved) calls a new `ReviewsController#merge_pr` action — distinct from the pre-existing `#merge` ("combine several post-commit reviews into one," untouched) — which calls the platform's own native merge endpoint (`Repository#merge_pull_request`, GitLab "Accept MR" / GitHub "Merge PR") rather than Codeveira performing a git-level merge itself. License-gated at Extended (`pr_mode`).
- **Pull Request Mode extended to Gitea and Forgejo** (Extended) — the next lowest-effort platforms after GitLab/GitHub, since `fetch_compare_diff`/`fetch_commit_parent_sha` already worked for `gitea_compatible?` repositories (built for the pre-existing post-commit path); Bitbucket Cloud/Server and Azure DevOps remain unsupported for PR mode since their diff-fetching plumbing doesn't exist yet, and Gerrit is architecturally excluded (its "change" model already collapses push and review into one unit, with no separate open/sync/merge lifecycle to hook into). `Repository#merge_pull_request` gained a `gitea_compatible?` branch calling the platform's native merge endpoint (`POST /api/v1/repos/{owner}/{repo}/pulls/{index}/merge`); `ProcessPullRequestJob` gained a `perform_gitea` handler reusing the exact same `open_pull_request`/`sync_pull_request`/`finalize_pull_request` logic already built for GitLab/GitHub, since Gitea's `pull_request` webhook payload shape mirrors GitHub's (its "new commits pushed" action is spelled `synchronized`, not `synchronize`). Enable per repository via **Edit → Pull Request Mode** (now GitLab/GitHub/Gitea/Forgejo), then turn on "Pull Request" on that repository's existing Gitea/Forgejo webhook.
- **Pull Request Mode extended to Bitbucket Cloud, Bitbucket Server, and Azure DevOps** (Extended) — closes the three-platform gap left by the entry above. All three turned out to genuinely support both "diff between two arbitrary commits" and a native merge endpoint, so the earlier "diff-fetching plumbing doesn't exist yet" note was a build gap, not an architectural blocker like Gerrit's. New `fetch_bitbucket_compare_diff`/`fetch_bitbucket_server_compare_diff`/`fetch_azure_compare_diff` each reuse an existing single-commit diff endpoint's two-revision form and, for Bitbucket Server/Azure, the same JSON-to-diff converter already built for the single-commit case — wired into the same `fetch_compare_diff` dispatch the whole open/synchronize lifecycle already relies on. `Repository#merge_pull_request` gained three new branches: Bitbucket Cloud's `POST .../pullrequests/{id}/merge`; Bitbucket Server's merge, which reads the PR's current `version` first for optimistic-concurrency locking before posting; and Azure's `PATCH .../pullrequests/{id}` with `status: "completed"`. Bitbucket Cloud and Bitbucket Server are the only two platforms whose webhook event type arrives solely via the `X-Event-Key` HTTP header rather than the payload body, so `ProcessPullRequestJob#perform` gained a 4th `event` argument threaded through from the webhook controller just for those two. Azure's webhook has a real quirk worth calling out: there's no distinct "PR closed" event — merged and abandoned both arrive via `git.pullrequest.updated` with a `status` field, and the separate `git.pullrequest.merged` event fires on a merge *attempt* that can still fail, so it's only treated as a confirmed merge when the resource's `status` reads `completed`. Enable per repository via **Edit → Pull Request Mode**, now covering all seven non-Gerrit platforms; turn on the matching PR/pull-request event on that repository's existing webhook config.
- **Pull Request Mode extended to Gerrit, via its native patch-based Change model** (Extended) — closes the last platform gap; what earlier entries called an architectural blocker turned out to be a naming mismatch, not a real one. Gerrit has no PR/MR object, but its Change lifecycle (open → new patch-set → submit/abandon) maps onto the same open/sync/finalize shape the other seven platforms already use — it just needed its own job rather than another `ProcessPullRequestJob` branch. New `review_kind: 'gerrit_change'` (alongside the existing `'pull_request'`) reuses every PR-mode column with no migration; `Review#live_tracked?` (`pull_request? || gerrit_change?`) is the new umbrella predicate the UI/controller gate on instead of `pull_request?` alone. New `ProcessGerritChangeJob`, fully separate from `ProcessPullRequestJob`, dispatches on the Gerrit event `type`: `patchset-created` (patch-set 1 opens, >1 syncs an incremental commit and resets approvals), `change-merged` (finalizes as merged, capturing the event's `newRev` — the actual landed SHA, which can differ from the last patch-set's own revision under Cherry Pick/Rebase Always — into `pr_head_sha`), `change-abandoned` (finalizes as closed), `change-restored` (reopens). New `Repository#submit_gerrit_change` posts a `Code-Review: +2` label then calls Gerrit's own `submit` endpoint, wired as one more branch of the existing `merge_pull_request` dispatch so the Merge button needed no new controller action. One real correctness wrinkle: Gerrit also fires its existing `ref-updated` event when a tracked Change lands, which would otherwise create a second, duplicate review for the same commit alongside the one `ProcessGerritChangeJob` already created — `ProcessPushJob#perform_gerrit` now skips creating a review if a `gerrit_change`-kind review already has that commit as its `pr_head_sha`. Enable per repository via **Edit → Pull Request Mode**, now covering all eight platforms; on Gerrit, configure the `webhooks` plugin (or equivalent) to POST `patchset-created`/`change-merged`/`change-abandoned`/`change-restored` to the existing `/webhooks/gerrit` endpoint.
- **Generic SAST findings ingestion via SARIF** (Enterprise) — new `POST /webhooks/ci/sast` endpoint ingests **SARIF 2.1.0** reports, the JSON standard emitted by Semgrep, CodeQL, Bandit, Brakeman, Trivy, Checkov, and effectively every modern SAST/security scanner, so one integration covers the whole ecosystem rather than a bespoke adapter per vendor. Same multipart shape and `X-Codeveira-Token` auth as the existing coverage webhook (`commit_sha`, optional `pipeline_name`, `report` file). `SarifReportParser` merges `runs[].results[]` across the report into a uniform finding list, tolerating multiple runs, `file://`-prefixed URIs, and results with no location. Each finding is posted as a real inline review comment from a dedicated `sast-bot` account — the same "a finding is just an unresolved inline comment" mechanism Architectural Lint and Duplicate Code Detection already use — deduped so re-uploading the same report doesn't repost. A new summary card on the review page shows total findings by severity, tool name, and pipeline name, with a staleness warning if the report predates the review's current HEAD commit. License-gated at the same tier as Code Coverage (`sast_findings: 'enterprise'`).
- **Admin notifications for scheduled/manual database backups** — every admin now gets an in-app notification (`/notifications`) reporting whether each backup succeeded (with the resulting filename) or failed (with the error), fixing a real gap: `DatabaseBackupJob` previously only logged a failure and overwrote an `AppSetting` status field on `pg_dump` failure, without raising — so the job never landed in Sidekiq's retry/dead sets, and the only trace of a silent failure was a log line in a container whose logs are gone after the next `docker compose build`/restart. `Notification.notify_admins(event:, message:)` (new class method, targets `User.humans.where(admin: true)`) creates a review-less system notification for `backup_succeeded`/`backup_failed`; required making `notifications.review_id` nullable and adding a `message` column, both backward compatible with every existing review-based notification path (index page, unread-count polling, mark-read — all confirmed to tolerate a `nil` `review_id`). The `/notifications` page renders these with a green check / red X instead of an actor avatar, linking to **Settings → Backup & Restore**. Fires on a `pg_dump` exit failure, on any exception raised during the job, and on success.
- **Native Task Tracker integration: YouTrack, Jira, Mantis, Bugzilla** (Standard) — closes the gap the outgoing-webhooks `ticket_keys` work below could only work around: instead of requiring the customer to hand-write a receiving automation on the tracker's side, Codeveira now transitions the ticket's status and posts a comment back directly. New **Settings → Task Trackers** (global default) + per-repository **Task Trackers** tab (opt-in override, "Use this repository's own task trackers" on the Edit page) — same global/override shape `Outgoing Webhooks` already established, `repository_id` nullable from the first migration since global-capable was the design from day one, unlike `outgoing_webhooks`' two-migration history. Configure a base URL + API token per tracker (Jira also needs the account email, for Basic Auth) and map each review lifecycle event (`review.opened/approved/rejected/closed/reopened`) to a target ticket status — no separate event checkboxes, the mapped events list derives automatically from which events have a status configured. All four adapters use plain `Net::HTTP` (no new HTTP client dependency) with the SSRF guard re-checked at request time, not just at save time: **YouTrack** applies the target state name directly; **Jira** looks up the issue's real available transitions and matches the configured name case-insensitively, failing with the actual valid names listed if there's no match; **Mantis** validates the target against the project's status enum before applying it, and surfaces a clear error rather than a silent no-op if the REST API is disabled server-side; **Bugzilla** sets `status` and `resolution` together in one request, matching its classic two-field close workflow. Mantis and Bugzilla both key issues by a bare number, not `PROJECT-123`-style keys — reuses the existing per-repository `issue_key_pattern` override (the same setting `ticket_keys` extraction below already added) rather than a new setting. A **Test Connection** button verifies the base URL and credentials before relying on them. Sync runs async on the same review lifecycle events `Outgoing Webhooks`/`fire_outgoing_webhook` already hooks — fired additively alongside it, not replacing it — and a tracker-side failure is logged, never blocks the review action that triggered it. Inbound direction (tracker → Codeveira) is out of scope.
- **Real semantic analysis, Phase 1: Go/gopls** (Enterprise) — opt-in per repository (**Edit page → "Enable real semantic analysis (Go)"**, same toggle pattern as the outgoing-webhooks override), a new subsystem alongside (not a replacement for) the existing tree-sitter symbol indexer: drives the real `gopls` language server against the repository's Go module, so its diagnostics are actual `go vet`/compiler output and its definitions are type-resolved rather than name-matched. Triggers automatically on every push via a new `semantic-analysis` container (`POST /analyze`, shared-secret auth), guarded by a coalescing check that skips (rather than queues) a new run if one is already in progress for that repository/branch. Rails is the only thing that ever talks to your git host — it fetches the repository archive itself (GitLab only, for now) and streams it to the container over the internal Docker network; the container never talks to your git host at all. Because this is the first Codeveira feature to run a target repository's own dependency-install tooling (`go mod download`), it ships with a real egress allow-list from day one: a new `semantic-analysis-proxy` container restricts the analysis container's only route to the internet to `proxy.golang.org`/`sum.golang.org`/`storage.googleapis.com`, the Go module proxy's own domain set. New review-page "Semantic Analysis" panel shows run status, definition/diagnostic counts, a staleness warning if the run's commit doesn't match the review's current HEAD, and a diagnostics list linking into the diff at each finding's file. New `SEMANTIC_ANALYSIS_TOKEN`/`SEMANTIC_ANALYSIS_MEM_LIMIT`/`SEMANTIC_ANALYSIS_CPUS` env vars. Not yet built: other languages (TypeScript, Java, Kotlin, Python, PHP, C#, Ruby), a typed Find-Usages/Go-to-Definition upgrade, diagnostics inlined into diff hunks, non-GitLab archive fetching
- **Real semantic analysis, Phase 2: TypeScript** (Enterprise) — a second opt-in language on the same subsystem Phase 1 shipped, not a rebuild of it: a new `semantic_analysis_language` column on `Repository` (`go`/`typescript`/`python`, default `go`) drives a **Language** dropdown next to the existing "Enable real semantic analysis" toggle on the repository Edit page (the toggle's own label dropped the "(Go)" suffix now that it covers all three). Drives `typescript-language-server` as an LSP subprocess exactly like Phase 1 drives `gopls` — `.ts`/`.tsx` files, plus `.js`/`.jsx` alongside them, requires a `tsconfig.json` at the workspace root to run at all, and conditionally runs `npm ci --ignore-scripts` (not full `npm install`) when a `package.json` is present. New `semantic-analysis-ts` container (its own Dockerfile, port `8093` alongside Go's `8092`) and its own dedicated egress-allowlist proxy, `semantic-analysis-ts-proxy` (tinyproxy, scoped to `registry.npmjs.org` only) on its own internal-only Docker network (`semantic_analysis_ts_net`) — fully separate from Go's `semantic-analysis-proxy`/`semantic_analysis_net`, not shared, so each sandboxed language keeps its own toolchain and its own dependency-execution trust boundary. New `SEMANTIC_ANALYSIS_TS_URL`/`SEMANTIC_ANALYSIS_TS_TOKEN`/`SEMANTIC_ANALYSIS_TS_MEM_LIMIT`/`SEMANTIC_ANALYSIS_TS_CPUS` env vars, following the exact same pattern as the existing Go vars, which are unchanged. The review-page "Semantic Analysis" panel, the `semantic_analysis_runs`/`semantic_definitions`/`semantic_diagnostics` tables, and the persistence path are all shared and language-agnostic — no per-language table split.
- **Real semantic analysis, Phase 2: Python** (Enterprise) — a third opt-in language on the same subsystem, drives `pyright` (via `pyright-langserver --stdio`) exactly like Go drives `gopls` and TypeScript drives `typescript-language-server`. Python has no single canonical project manifest, so the new `semantic-analysis-py` container gates a run on any of `pyproject.toml`/`requirements.txt`/`setup.py`/`setup.cfg`/`Pipfile`/`pyrightconfig.json` being present at the workspace root, rather than requiring one specific file. When `requirements.txt` is present, dependencies are installed into an isolated venv with `pip install --only-binary=:all:` — pip has no `--ignore-scripts` equivalent (an sdist install always runs `setup.py`/build-backend code), so restricting to prebuilt wheels only (pure archive extraction, no code execution) is the mitigation; a dependency with no available wheel is skipped and logged rather than failing the run. A `pyrightconfig.json` pointing at the venv is written automatically unless the repository already ships its own, so installed dependencies' types are actually visible to `pyright`. New `semantic-analysis-py` container (its own Dockerfile, port `8094`) and its own dedicated egress-allowlist proxy, `semantic-analysis-py-proxy` (tinyproxy, scoped to `pypi.org`/`files.pythonhosted.org` only) on its own internal-only Docker network (`semantic_analysis_py_net`) — fully separate from the Go and TypeScript proxies/networks. New `SEMANTIC_ANALYSIS_PY_URL`/`SEMANTIC_ANALYSIS_PY_TOKEN`/`SEMANTIC_ANALYSIS_PY_MEM_LIMIT`/`SEMANTIC_ANALYSIS_PY_CPUS` env vars, following the exact same pattern as the Go/TypeScript vars.
- **Real semantic analysis, Phase 2: Java** (Enterprise) — a fourth opt-in language on the same subsystem, drives Eclipse JDT Language Server (`jdtls`) exactly like the other three drive their respective language servers. **Maven-only scope**: the new `semantic-analysis-java` container gates a run on a `pom.xml` at the workspace root — Gradle's `build.gradle`/`build.gradle.kts` are executable Groovy/Kotlin scripts evaluated just by importing the project, unlike declarative XML `pom.xml`, so Gradle-only repos are skipped rather than weakening the trust boundary the other three languages protect. Dependencies are resolved with `mvn dependency:resolve` run as a standalone goal — Maven only executes plugins bound to the lifecycle phases actually invoked, so this populates `~/.m2` without running the project's own compiler/packaging plugins, the Maven-shaped equivalent of TypeScript's `--ignore-scripts` and Python's `--only-binary=:all:`. New `semantic-analysis-java` container (its own Dockerfile, port `8095`) and its own dedicated egress-allowlist proxy, `semantic-analysis-java-proxy` (tinyproxy, scoped to `repo1.maven.org`/`repo.maven.apache.org` only — Maven Central's two live endpoints) on its own internal-only Docker network (`semantic_analysis_java_net`) — fully separate from the Go/TypeScript/Python proxies and networks. New `SEMANTIC_ANALYSIS_JAVA_URL`/`SEMANTIC_ANALYSIS_JAVA_TOKEN`/`SEMANTIC_ANALYSIS_JAVA_MEM_LIMIT`/`SEMANTIC_ANALYSIS_JAVA_CPUS` env vars, following the exact same pattern as the other three. Notable integration quirk found and fixed during development: Maven's own HTTP transport (Aether) ignores JVM proxy system properties and `HTTP_PROXY`/`HTTPS_PROXY` env vars entirely — unlike pip/npm, which both honor `HTTP_PROXY`/`HTTPS_PROXY` natively, Maven only reads proxy config from `~/.m2/settings.xml`'s `<proxies>` block, which the container now writes at startup from the injected proxy env vars; without this fix both `mvn dependency:resolve` and `jdtls`'s own bundled Maven project importer failed silently, returning empty results with no error surfaced. Not yet built (either phase): other languages (Kotlin, PHP, C#, Ruby), Gradle support for Java, a typed Find-Usages/Go-to-Definition upgrade (still tree-sitter-based navigation for all four), diagnostics inlined into diff hunks (still a standalone review-page panel), dependency-install caching (every run does a fresh `npm ci`/`go mod download`/`pip install`/`mvn dependency:resolve`), yarn/pnpm lockfile support for TypeScript (npm/`package-lock.json` only), `pyproject.toml`/Poetry/Pipenv support for Python (`requirements.txt` only)
- **Real semantic analysis, Phase 2: Kotlin** (Enterprise) — a fifth opt-in language on the same subsystem, drives the MIT-licensed `fwcd/kotlin-language-server` over the same **Maven-only scope** Java uses: the new `semantic-analysis-kt` container gates a run on a `pom.xml` at the workspace root, same Gradle-exclusion reasoning as Java (`build.gradle`/`build.gradle.kts` are executable scripts evaluated at project-import time — a bigger real-world trade-off here than it was for Java, since most Kotlin projects use Gradle rather than Maven, but the trust boundary comes first). Two real Kotlin language servers exist: the official `Kotlin/kotlin-lsp` (JetBrains, actively developed) and the community `fwcd/kotlin-language-server` (older, self-described as "considered deprecated" now that an official one exists). The official server was evaluated first, but its own README discloses it "incorporates proprietary parts of JetBrains Air and Fleet products, making it partially closed-source," and the repo is a "read-only mirror" — a real redistribution risk given this project's CI publishes built images publicly to `ghcr.io`, not a hypothetical one. `fwcd/kotlin-language-server` was chosen instead: MIT licensed, zero redistribution ambiguity, at the cost of a less actively developed upstream. Unlike Java's driver, there is no separate `mvn dependency:resolve` step before spawning the language server — `kotlin-language-server` resolves its own Maven classpath internally (`mvn dependency:list`/`dependency:sources`, both standalone goals, same non-execution guarantee as Java's `dependency:resolve`), so the driver only needs to write the proxied `~/.m2/settings.xml` and let the language server trigger resolution itself. New `semantic-analysis-kt` container (its own Dockerfile, port `8096`) and its own dedicated egress-allowlist proxy, `semantic-analysis-kt-proxy` (tinyproxy, scoped to `repo1.maven.org`/`repo.maven.apache.org`, the same two Maven Central endpoints as Java's proxy) on its own internal-only Docker network (`semantic_analysis_kt_net`) — fully separate from the Go/TypeScript/Python/Java proxies and networks. New `SEMANTIC_ANALYSIS_KT_URL`/`SEMANTIC_ANALYSIS_KT_TOKEN`/`SEMANTIC_ANALYSIS_KT_MEM_LIMIT`/`SEMANTIC_ANALYSIS_KT_CPUS` env vars, following the exact same pattern as the other four. Not yet built (any phase): other languages (PHP, C#, Ruby), Gradle support for Java and Kotlin, a typed Find-Usages/Go-to-Definition upgrade (still tree-sitter-based navigation for all five), diagnostics inlined into diff hunks (still a standalone review-page panel), dependency-install caching (every run does a fresh `npm ci`/`go mod download`/`pip install`/`mvn dependency:resolve`/`kotlin-language-server`'s own Maven resolution), yarn/pnpm lockfile support for TypeScript (npm/`package-lock.json` only), `pyproject.toml`/Poetry/Pipenv support for Python (`requirements.txt` only), revisiting the official `Kotlin/kotlin-lsp` if its licensing situation is ever clarified favorably for public image redistribution
- **Real semantic analysis, Phase 2: PHP** (Enterprise) — a sixth opt-in language on the same subsystem, drives the MIT-licensed `vimeo/psalm`'s bundled `psalm-language-server` — a real type-checking static-analysis engine, the closest PHP analogue to pyright's role for Python. Two other real options were evaluated first: Intelephense (best-in-class IDE experience, but closed-source/commercial — the same public-image-redistribution licensing risk that ruled out the official `Kotlin/kotlin-lsp`) and Phpactor (MIT, but historically oriented around completion/refactoring rather than deep type-checked diagnostics); Psalm was chosen for the combination of real type inference and unambiguous MIT licensing. The new `semantic-analysis-php` container gates a run on a `composer.json` at the workspace root (single-marker-file check, same shape as Java/Kotlin's `pom.xml` gate; no `composer.lock` requirement), then runs `composer install --no-scripts --no-plugins --no-interaction` — Composer, unlike Maven, honors lowercase `http_proxy`/`https_proxy` env vars natively in CLI context, so no settings-file plumbing was needed. Packagist (`repo.packagist.org`) only serves package *metadata*, not the actual `dist` downloads — those come directly from `codeload.github.com`/`api.github.com`/`objects.githubusercontent.com` for GitHub-hosted packages (the large majority of the PHP ecosystem) — so the new `semantic-analysis-php-proxy` (tinyproxy) allow-lists all four hosts, wider than every prior language's proxy; GitLab/Bitbucket/self-hosted-VCS-hosted Composer packages will fail dependency resolution, logged as a remainder. Two Psalm-specific quirks discovered during development: Psalm refuses to run at all without a `psalm.xml` config file, so the driver writes a minimal default one only if the target repo doesn't already have one; and `psalm-language-server` doesn't implement `textDocument/documentSymbol` (confirmed via a live `-32601` LSP error), so PHP's `definitions` array is always empty — this is a diagnostics-only language, unlike the other five. New `semantic-analysis-php` container (its own Dockerfile, port `8097`) on its own internal-only Docker network (`semantic_analysis_php_net`), fully separate from the other five proxies and networks. New `SEMANTIC_ANALYSIS_PHP_URL`/`SEMANTIC_ANALYSIS_PHP_TOKEN`/`SEMANTIC_ANALYSIS_PHP_MEM_LIMIT`/`SEMANTIC_ANALYSIS_PHP_CPUS` env vars, following the exact same pattern as the other five. - **Semantic analysis: per-language dependency-install caching** (Enterprise) — closes the "dependency-install caching" gap every one of the eight language entries above listed as not-yet-built. Rather than a hand-rolled lockfile-hash-keyed save/restore cache, each container now mounts a persistent named Docker volume at its package manager's own existing content-addressed cache directory (name+version-keyed, or content-hash-keyed for pip), so nothing new has to hash a lockfile, look up a snapshot, or evict anything — the package manager already handles concurrent access to a shared cache dir safely, the same assumption any CI system relies on when reusing a cache dir across parallel jobs. This is also strictly better than a literal lockfile-hash cache: it's reused across every repository analyzed for that language, not just repeat runs of the identical repo. Ruby is the one real behavior change rather than a pure mount: gems previously installed into `vendor/bundle` inside the ephemeral per-request workspace by design (to avoid writing into a shared path the container user might not own); they now install to a persistent `/home/analyzer/.cache/bundle`, owned by the same non-root `analyzer` user every other language's cache dir already uses, so that original concern no longer applies. No new env vars or `.env.example` changes — cache paths are internal container details, same as the pre-existing `GOPATH`/`NPM_CONFIG_CACHE`/`PIP_CACHE_DIR`. Trust boundary unchanged: the cache only ever holds package content that already passed through that language's existing egress-allowlist proxy under the same install flags as before, never target-repo source; the new, real limitation is that these volumes have no automatic eviction or size cap and grow unboundedly like any CI package cache — clear one manually with `docker volume rm` if disk usage becomes a concern.

### Fixed
- **JetBrains plugin was silently disabled on every real install** — `plugin.xml` declared `<depends>com.intellij.platform.lsp</depends>`, but that's not a real plugin ID in any IntelliJ distribution, so the dependency could never resolve and the whole plugin loaded disabled — every setting, tool window, and action was unavailable. LSP support (`LspServerManager`, `platform.lsp.serverSupportProvider`, etc.) is actually baked directly into the IDE's core platform plugin and needs no separate dependency declaration; the bogus `<depends>` line has been removed. Found while adding the plugin's first JVM test suite (JUnit + IntelliJ Platform test framework), which surfaced the disabled-plugin state immediately.
- **Semantic Analysis (Go/TypeScript/Python) was undeployable from this compose file** — `semantic-analysis`, `semantic-analysis-ts`, and `semantic-analysis-py` (plus their three dedicated egress-allowlist proxies) were documented in this README/CHANGELOG/`.env.example` but never actually wired into `docker-compose.yml`, so enabling the feature on a repository would just fail with unreachable sidecar errors — the deploy compose file simply had no service blocks for any of the three languages, even though the main source repo's own `docker-compose.yml` (build-from-source) has had them since each language shipped. Added all six service blocks (`image: ghcr.io/codeveira/codeveira-semantic-analysis[-ts|-py][-proxy]`), their three `internal: true` networks, and the matching `SEMANTIC_ANALYSIS[_TS|_PY]_URL`/`_TOKEN` env vars + `depends_on` entries on `sidekiq`. The CI workflow (`.github/workflows/docker.yml`) is also updated to actually build and push those six images to `ghcr.io` — they didn't exist there before either, which is why this went unnoticed.
- **Encrypted settings could silently return raw ciphertext instead of failing loudly** — if a stored value couldn't be decrypted under the currently configured `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY` (most plausibly: a database backup restored into an environment with a different encryption key than the one it was created under), `AppSetting.get` used to hand back the raw encrypted blob as if it were the plaintext value, thanks to Rails' `support_unencrypted_data` compatibility setting silently swallowing the decryption error. Now detects Active Record Encryption's own envelope shape on the returned value and treats it as unset (with an error logged naming the affected setting) instead of leaking ciphertext into any page, webhook payload, or log line that reads it — affects all 100+ call sites across the app, not just the one (Checklist Enforcement's repository Edit page) it was first spotted on.
- **Settings forms silently discarding their success/error message in the browser** — a layout-wide `<meta name="turbo-visit-control" content="reload">` tag (added for an unrelated reason) caused Turbo Drive to silently drop the flash message on nearly every Settings form submission — both validation errors and successful saves — making a save look like it did nothing, or like a choice had silently reverted. Fixed across every affected Settings page (Domain & HTTPS, License, AI Prompts, Review Templates, Access Control, Audit Log, Checklist Enforcement, Architectural Lint, Notifications, Users, Backup & Restore, Upsource Import, CI Integration, Webhook Deliveries).
- **Backup schedule always active** — scheduled database backup (`database_backup` Sidekiq Cron job) is now registered at Sidekiq startup even when the user has never explicitly clicked **Save schedule**; default schedule is daily at 3:00 AM UTC
- **Backup upload** (Standard) — **Upload Backup** section added to Settings → Backup & Restore; drag & drop or file picker to upload a `.dump` file from your computer; uploaded file appears in the Saved Backups list immediately and can be restored like any other snapshot; nginx `client_max_body_size` raised from 10 MB to 512 MB to accommodate large dump files
- **Backup & Restore progress UI** (Standard) — real-time feedback for backup and restore operations: clicking **Backup now** shows a live spinner banner; on completion the banner turns green with the backup filename and the page auto-reloads; clicking **Restore** shows a full-screen blocking overlay with a spinner; when the restore finishes the overlay transitions to a green confirmation with an **OK** button that reloads the page; works correctly even after restore invalidates the user session

### Changed
- **Database backups now write to a host-bind-mounted `./backup` directory instead of the `backup_data` Docker named volume** — dump files are directly visible/browsable on the host without `docker compose exec`/`docker volume inspect`, are trivial to point an external rsync/restic/cloud-sync job at, and — unlike a named volume — survive `docker compose down -v`, so they're no longer at risk of being wiped alongside the live database in the same command. **Action required on upgrade:** the `backup_data` volume isn't deleted automatically and your existing dumps stay in it; copy them into the new `./backup` directory before removing the old volume, e.g. `docker run --rm -v <project>_backup_data:/from -v "$(pwd)/backup":/to alpine cp -a /from/. /to/` (run once, then `docker compose up -d app sidekiq` to pick up the new mount, then optionally `docker volume rm <project>_backup_data`). Nothing to do if you already customized `BACKUP_DIR`/the volume mapping to a bind mount yourself, per the earlier docs.
- **PostgreSQL and Redis data now live in host-bind-mounted `./pgdata` and `./redis` directories instead of the `db_data`/`redis_data` Docker named volumes** — same reasoning as the backup change above, one level more important: unlike backups, `db_data`/`redis_data` held the *only* live copy, so `docker compose down -v` (including via this project's own documented `TESTSERVICE` demo-data-reset instructions) could previously destroy the live database itself, not just a safety net. **Action required on upgrade — this touches your live database, read before running:**
  1. Stop the app so nothing writes during the migration: `docker compose stop app sidekiq`
  2. Stop `db` and `redis` themselves — required, copying a running Postgres data directory can silently produce a corrupt copy: `docker compose stop db redis`
  3. Copy each old volume into its new directory: `docker run --rm -v <project>_db_data:/from -v "$(pwd)/pgdata":/to alpine cp -a /from/. /to/` and `docker run --rm -v <project>_redis_data:/from -v "$(pwd)/redis":/to alpine cp -a /from/. /to/`
  4. `docker compose up -d` to pick up the new mounts, then confirm your existing data is there (log in, check a known review exists) before doing anything else
  5. Only once you've confirmed the data is intact, optionally remove the old volumes: `docker volume rm <project>_db_data <project>_redis_data`

  Nothing to do on a fresh install — `./pgdata` and `./redis` are created empty and initialized normally on first boot.
