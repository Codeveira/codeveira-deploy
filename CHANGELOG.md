# Changelog

All notable changes to Codeveira are documented here.

## [Unreleased]

### Security

- **`docker-compose.local-model.yml`'s bundled Ollama image bumped from `0.16.4` to `0.33.0`.** The old pin predated the fix for CVE-2026-7482 ("Bleeding Llama") — a critical unauthenticated heap-memory-leak vulnerability in Ollama's GGUF loader that lets an attacker extract a server's entire process memory (env vars, API keys, other users' in-flight prompts) via three unauthenticated API calls, fixed upstream in 0.17.1. Anyone running the optional local-model overlay should pull the new image (`docker compose -f docker-compose.yml -f docker-compose.local-model.yml pull ollama && ... up -d`).
- **`app` and `lsp` no longer publish their ports directly to the host — only the bundled `nginx` container does.** Previously `app:3000` and `lsp:7777` were published to the host *in addition to* nginx's `443`/`80`, so anyone could reach either one directly in plain HTTP/TCP, bypassing nginx and TLS entirely regardless of Domain & HTTPS configuration — `FORCE_SSL=true` didn't fully close this, since the first request (session cookie, login password) still traveled in cleartext before any redirect could fire. **Action required if you run your own external reverse proxy instead of the bundled nginx** ("Bring your own reverse proxy" in the README): merge the new `docker-compose.byo-proxy.yml` (`docker compose -f docker-compose.yml -f docker-compose.byo-proxy.yml up -d`) to republish those two ports, and comment out the bundled nginx's own `ports:` block by hand (Compose can't subtract it via an override). Everyone using the bundled nginx (the default, recommended setup) needs no action — `docker compose up -d` already only publishes 80/443/7777 from nginx now.
- **Repository access control (IDOR) fix** — `Browse`, `Reviews`, `Comments` (including posting new comments), `Labels`, `Commits`, and the repository overview/README/metrics/analytics pages now correctly scope repository lookups to repos the current user is a member of (or all repos for global admins). Previously any logged-in user could view — and in some cases modify — data belonging to a repository they weren't a member of, just by changing the numeric `repository_id` in the URL. The REST API and MCP server were already scoped correctly and are unaffected.
- **Azure DevOps and Gerrit webhooks now require authentication.** These platforms don't support HMAC payload signing the way GitLab/GitHub/Gitea/Bitbucket do, so requests are now authenticated via HTTP Basic Auth instead — set `AZURE_WEBHOOK_SECRET`/`GERRIT_WEBHOOK_SECRET` and configure the matching password on the webhook subscription/plugin config. **Action required on upgrade:** these webhooks will start rejecting requests with `401` until the new env vars are set and the receiving side is configured to send Basic Auth.
- **Encryption at rest for Repository access tokens, AI provider API keys, user API tokens, and sensitive settings** (CI webhook token, SMS API token, etc.) via Rails Active Record Encryption. **Action required on upgrade:** set `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`, `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY`, and `ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT` in `.env` before starting — the app won't boot without them. Existing values are re-encrypted automatically the next time `rails db:migrate` runs; nothing is lost or requires manual re-entry.
- **SSRF protection** for the repository instance URL (self-hosted GitLab/Gitea/Forgejo/Bitbucket Server/Azure DevOps/Gerrit), outgoing webhook URLs, and the AI reviewer's custom API URL — blocks cloud metadata endpoints and the app's own internal service names, while still allowing arbitrary internal hostnames and private IP ranges (required for these self-hosted/internal-network features to keep working).
- **Account lockout** — 10 failed login attempts locks an account for 1 hour, closing off online brute-force against `/users/sign_in`. Minimum password length raised from 6 to 8 characters.
- **Password-reset request rate limiting** — `/users/password` previously had no attempt limit at all, letting an attacker mass-email-bomb a victim's inbox by repeatedly requesting a reset for their address, or probe many addresses from one source. Now capped at 5 requests per email address and 20 requests per source IP, both per hour; a throttled request gets the exact same response as a real one, so the limiter itself can't be used to detect whether an email address has an account.
- **Homoglyph/lookalike username and email protection** — username and email uniqueness previously compared raw bytes only, so a Cyrillic "а" swapped for a Latin "a" (or the same name in a different Unicode normalization form) could create a second account that renders identically to an existing one — a real impersonation risk in @mentions and reviewer pickers. New accounts are now also checked against a Unicode-confusable "skeleton" of every existing username/email, rejecting visual lookalikes at creation time.
- **`FORCE_SSL` option** — set `FORCE_SSL=true` once TLS is terminated in front of the app to redirect HTTP→HTTPS and mark session cookies `Secure`.
- **Backup upload hardening** — uploaded `.dump` files are now checked against a maximum size (`MAX_BACKUP_UPLOAD_SIZE`, default 2GB) and a valid pg_dump custom-format signature before being accepted for restore.
- **Non-root containers** — `app`, `sidekiq`, `indexer`, and `lsp` now run their application process as a non-root user rather than root, reducing the impact of any future RCE in a dependency.
- **Upsource import SSRF check now enforced per-request**, not just once when the URL is first entered — closes a DNS-rebinding window during the (potentially long-running, re-runnable) import job.

### Added
- **Kubernetes deployment (Helm, MVP)** — `helm/codeveira/` alongside the docker-compose deployment, one subchart per service (`codeveira-app`, `codeveira-sidekiq`, `codeveira-postgresql`, `codeveira-redis`, `codeveira-ingress`, plus a `codeveira-common` library chart for shared naming/label/probe helpers). `codeveira-ingress` wires a native `Ingress` to `cert-manager` (either its own `ClusterIssuer` via ACME HTTP-01, or an existing one your platform team manages). The app now reads a new `DEPLOYMENT_PLATFORM` env var (`app/services/deployment_platform.rb`) — the Helm chart's `codeveira-app` Secret always sets it to `kubernetes`, which hides Settings → Domain & HTTPS (nav tab, feature card, and the controller's own actions all reject/hide) since `cert-manager` owns certificate issuance/renewal at the cluster level there instead of the in-app nginx/certbot flow. Leave `DEPLOYMENT_PLATFORM` unset for docker-compose — nothing changes there. Each subchart can also be installed standalone; see `helm/codeveira/README.md` for install instructions, required secrets, and known MVP limitations (`emptyDir` storage by default, autoscaling disabled due to a migration race in `entrypoint.sh`, `DatabaseBackupJob` still needs its own writable mount).
- **Kubernetes deployment (Helm) — three more optional subcharts**: `codeveira-indexer`, `codeveira-lint-runner`, `codeveira-lsp`, mirroring the docker-compose `indexer`/`lint-runner`/`lsp` services (symbol indexing, Architectural Lint/duplicate-detection, and the global LSP proxy for IDE integration respectively). All three are **disabled by default**, same as they're non-mandatory in docker-compose. Enable with e.g. `--set codeveira-indexer.enabled=true`; `codeveira-app`/`codeveira-sidekiq` already default their `SYMBOL_INDEXER_URL`/`LINT_RUNNER_URL` to these subcharts' fixed Service names, so no extra wiring is needed. Their optional-but-recommended auth tokens can now be set once via the umbrella chart's new `global.integrations.symbolIndexerToken`/`lintRunnerToken`/`lspProxySharedSecret`, instead of duplicating the value in both the feature subchart and `codeveira-app`/`codeveira-sidekiq`. `codeveira-lsp`'s Service stays `ClusterIP`-only for now — external exposure of its raw TCP port 7777 (LoadBalancer vs. an ingress-nginx TCP ConfigMap entry) is a deliberately still-open decision, see `helm/codeveira/README.md`.
- **Kubernetes deployment (Helm) — `codeveira-semantic-analysis` subchart**, mirroring docker-compose's 8 per-language `semantic-analysis[-<lang>]`/`semantic-analysis[-<lang>]-proxy` service pairs (go/ts/py/java/kt/php/csharp/ruby). Disabled by default like the other feature subcharts, with a second toggle layer underneath: each language is independently enabled via `languages.<name>.enabled=true`, since a given repository only ever uses one. `languages` is a values *map* (not a list) specifically so a partial override (turning on one language) can't silently drop that language's other fields — see the comment at the top of `charts/codeveira-semantic-analysis/values.yaml`. Each enabled language gets a persistent 5Gi PVC for its dependency-install cache (go mod/npm/pip/.m2/composer/NuGet/bundler) so the drivers' existing cache-eviction pass has something durable to bound; tokens can be set once via `global.integrations.semanticAnalysisTokens.<name>`, same pattern as the other feature subcharts. Known limitation: the php sandbox's proxy does not receive the dynamic self-hosted-VCS allowlist that `ComposerProxyFilter`/`RegenerateComposerProxyFilterJob` write in the docker-compose deployment (would require a `ReadWriteMany` volume shared across two subcharts) — only GitHub-hosted Composer packages are reachable through it in this chart.
- **Kubernetes deployment (Helm) — `codeveira-redis-sentinel` and `codeveira-monitoring` subcharts**, the last two optional subcharts in the phased plan. `codeveira-redis-sentinel` is an HA overlay mirroring `docker-compose.sentinel.yml`'s shape: it does not replace `codeveira-redis` (which stays the initial Sentinel-monitored master), it adds a `redis-replica` Deployment plus a fixed-name (not release-derived, so its per-ordinal DNS is predictable), 3-pod `redis-sentinel` StatefulSet (quorum 2-of-3) alongside it — replica count is intentionally fixed at 3, not configurable, since `codeveira-app`/`codeveira-sidekiq`'s default `redisSentinel.hosts` is a literal 3-entry list. Enabling it (`codeveira-redis-sentinel.enabled=true` + `global.redis.sentinelEnabled=true`, or the equivalent per-subchart override) sets `REDIS_SENTINELS`/`REDIS_MASTER_NAME` in `codeveira-app`/`codeveira-sidekiq`'s Secret alongside the existing `REDIS_URL` — the app's own `lib/redis_sentinel_config.rb` switches into Sentinel mode purely off `REDIS_SENTINELS`'s presence, so no other wiring was needed. `codeveira-monitoring` is a genuinely thin wrapper, not a ported monitoring stack: unlike `docker-compose.monitoring.yml` (its own Prometheus/Grafana/Loki/Promtail containers), it deploys zero workload pods, assuming an existing Prometheus Operator + Grafana install (e.g. `kube-prometheus-stack`) is already on the cluster — it adds only a `ServiceMonitor` (CRD-guarded via `.Capabilities.APIVersions.Has`, so installing against a cluster without the Prometheus Operator CRDs skips that one resource instead of failing the whole render) pointing at `codeveira-app`'s `/metrics` with Bearer-token auth, and a labeled `ConfigMap` carrying a copy of the existing Grafana dashboard for the operator's sidecar to auto-import, with its datasource UID rewritten at template time to match the target cluster's own Grafana (`grafana.datasourceUid`, defaults to kube-prometheus-stack's own stock default). Requires an Extended-or-higher license and a service-account API token, same as the docker-compose monitoring stack's `/metrics` gate. Known limitation: the docker-compose stack's second dashboard (`nginx-security.json`, Loki-based nginx access-log analysis) has no Kubernetes equivalent, since this chart's ingress path has no bundled nginx container to scrape logs from. This closes out the full "Helm charts for Kubernetes" plan — every subchart in `IDEAS.md`'s phased build is now shipped.
- **Zero-downtime updates via `rollout.sh`** — a new script alongside `docker-compose.yml` upgrades the `app` service without a gap in service, for operators on plain Docker Compose (no Docker Swarm migration required). It starts a second `app` replica on the newly pulled image next to the running one, polls its new `/up` healthcheck route (also new — a plain, unauthenticated `rails/health#show` endpoint) until it passes, then removes the old replica; the bundled nginx already resolves the `app` hostname per-request via its `resolver` directive, so it picks up the new replica and drops the old one automatically, with no window where zero `app` containers are running. If the new replica never turns healthy within a timeout (default 120s, `HEALTH_TIMEOUT_SECONDS`), it's removed and the old replica is left serving, untouched. `sidekiq` is restarted normally (brief pause, not in the request path) only after `app` is confirmed healthy on the new image, since `entrypoint.sh` only runs `db:migrate` on `app`'s own boot path and `sidekiq` depends on that having already happened. Not compatible with `docker-compose.byo-proxy.yml`, which publishes `app:3000` directly to the host — a second replica can't bind the same port there; `rollout.sh` detects this and aborts with a pointer to the existing plain rollout instead. The plain `docker compose pull && up -d && exec app rails db:migrate` rollout in the Updating section still works exactly as before and remains the default for anyone who doesn't need zero-downtime.
- **Docker Swarm deployment** — `docker-swarm/` alongside `docker-compose.yml`, additive not a replacement. A full `docker-stack.yml` covering every service in the compose file (minus `test`/`selenium`, dev-only tooling that relies on Compose `profiles:`, unsupported under `docker stack deploy`), using the same pre-built `ghcr.io/codeveira/codeveira*` images this directory's `docker-compose.yml` already uses (`docker stack deploy` can't build images, so a `build:` context was never an option here). The real value is two things: native zero-downtime rolling updates (`deploy.update_config: order: start-first` + the existing `/up` healthcheck, `failure_action: rollback` on a bad deploy) as a drop-in replacement for `rollout.sh` under Swarm, and genuine horizontal scaling of the stateless workers (`app`, `sidekiq`, `indexer`, `lint-runner`, `lsp`, and 15 of the 16 `semantic-analysis-*`/`*-proxy` pairs) across however many nodes join the cluster, via `${APP_REPLICAS}`/`${SIDEKIQ_REPLICAS}`/`docker service scale`. Every named volume in this stack uses Docker's default `local` driver, which is per-node, not cluster-shared — so `db`, `redis`, `nginx`, `app`, `sidekiq`, and `semantic-analysis-php-proxy` (the one proxy that isn't stateless: it shares `php_composer_proxy_filter` with `app`/`sidekiq` for the dynamic Composer egress allow-list) are all placement-constrained to a single node labeled `codeveira.role=primary`, to stop Swarm from silently handing two services independent empty copies of what's supposed to be shared state. **Explicitly not high availability** — that single primary node remains a single point of failure, identical to the plain `docker-compose.yml` deployment; see `docker-swarm/README.md`'s "What you do NOT get" section for the full breakdown before relying on this for uptime guarantees. See `docker-swarm/README.md` for cluster setup, node labeling, and operating instructions.
- **Email/Patch Reviews — Linux-kernel-style `git format-patch` + `git send-email`** (Extended) — a fourth review model, alongside post-commit, PR mode, and Gerrit: a contributor mails a patch series directly to a repository's dedicated inbound address, and a maintainer reviews it by replying with a `Reviewed-by:`/`Acked-by:` trailer — no web UI round-trip required on either end. Deliberately minimal integration, built to reuse rather than add: the same inbound-mail infrastructure already wired for **Reply by Email** (`ActionMailbox`, self-hosted relay ingress, `INBOUND_EMAIL_DOMAIN`/`RAILS_INBOUND_EMAIL_PASSWORD`), the SVN/Gerrit precedent that a `Repository` can exist with no hosted API, and the existing unvalidated `review_kind` string column — no new license flag, it reuses `License::FEATURES[:pr_mode] = 'extended'` on the theory that this is a review model, not a plain post-commit snapshot. New `Repository#patch_inbox_token` (`has_secure_token`, unique) gives each repository its own `patch+<token>@<INBOUND_EMAIL_DOMAIN>` submission address, shown on its Edit page once source **Email/Patch** is selected. New `PatchEmailParser` (pure Ruby, no DB/API dependency) parses the standard `git format-patch` shape — series markers (`[PATCH n/m]`), cover letter, trailers, and the unified diff, which needs no new diff-parsing code since it's byte-identical to what every other source already produces. New `PatchSubmissionMailbox` routes `patch+...@` addresses (alongside the existing `reply+...@` rule), opens a review on the first patch/cover letter of a `git send-email` thread and appends every later patch in that thread as a new commit via new `ProcessEmailPatchJob` — a fresh thread (including a `v2` resend) always opens a new, separate review. `ReplyMailbox` gained trailer detection: a reply on an email-patch review containing `Reviewed-by:`/`Acked-by:` anywhere in the body approves that reviewer's assignment the same way an in-app approval does; a reply without one is posted as an ordinary comment. Not supported for this source, by design: repository browsing (tree/blame/file history — there's no hosted repo to browse), Autofix, and any semantic-analysis feature needing a full file. Merging is manual and out-of-band (`git am` locally, then close the review in the web UI).
- **Task tracker merge gate, CI/SAST merge gate, and reviewer auto-assignment by load** (Standard+/Enterprise) — three independent, opt-in checks configured per repository on the Edit page, all off by default with zero behavior change until configured, and a global admin can always override a block. **Task tracker merge gate** (Standard, requires the `task_trackers` license): set an allow-list of ticket statuses (e.g. "Done, Closed, Resolved") and approving/closing/merging a review is blocked while its linked Jira/YouTrack/Mantis/Bugzilla ticket sits in any other status — each adapter gained a new `current_status(ticket_key)` read reusing the same endpoint its existing `test_connection` already hits; fails open (never blocks) on a tracker API error, the same trade-off the existing tracker-sync job makes. **CI/SAST merge gate** (Enterprise, requires `ci_status`/`sast_findings`): two independent toggles — block on any failed CI pipeline status, and/or block on SAST findings at a configurable severity (errors only, or errors + warnings) — deliberately two separate settings rather than one combined toggle, so a repository can require green CI without also requiring a clean SAST scan, or vice versa. **Reviewer auto-assignment by load** (Standard, requires `reviewer_auto_assignment`): an opt-in alternative to the existing default of assigning every reviewer/admin on the repo — assigns only the N (configurable, default 2) least-loaded eligible reviewers, where "load" is itself configurable: open (pending) assignment count, or assignment count within a configurable recent-days window (default 30). The previously duplicated reviewer-assignment logic in `ProcessPushJob` and `ProcessPullRequestJob` was extracted into a new shared `ReviewerAssigner` service; the default (disabled) behavior is byte-for-byte unchanged.
- **Bus factor guard for reviewer assignment** (Standard, requires `reviewer_auto_assignment`) — an additive opt-in on top of reviewer auto-assignment by load: on a repository's Edit page, enabling `bus_factor_guard_enabled` (plus an optional owner-count threshold, default 2) force-assigns one extra reviewer who has never touched the review's changed files, whenever `CodeOwnershipService#distinct_owners_count` for those files is at or below the threshold — nudging knowledge-sharing before a low-bus-factor area becomes a single point of failure. Deliberately reuses `CodeOwnershipService` (already built for smart reviewer suggestions and ownership-based risk scoring) rather than inventing a new module-boundary or background-commit-analysis concept, and operates on the review's own changed files rather than any new per-folder aggregation. Always unioned onto whatever the load-based step already picked (or the full eligible pool, if auto-assignment is off) — never replaces or narrows it, so it's a zero-risk opt-in; no-ops when there's no ownership history yet or when every eligible reviewer is already familiar. Runs only once, at review-creation time, the same as the rest of `ReviewerAssigner` — it can't re-force a reviewer on every subsequent push to an existing review.
- **Scoped, expiring, individually-revocable REST API tokens** (Standard) — closes a real gap in the existing single-token model: every user previously had exactly one unscoped, non-expiring `api_token` (still used by MCP and Prometheus `/metrics`, and kept fully intact), so giving a CI pipeline REST API access meant handing it a token that could also read/write every other repository the user could, forever, with no way to revoke just that one integration. New `ApiToken` model — a user can now hold many side by side, each independently named, restricted to `read_only` or `read_write`, optionally scoped to a single repository, optionally set to expire, and independently revocable. Unlike the legacy column's reversible encryption, only a SHA-256 digest is ever stored — the raw value is shown once at creation and can't be recovered afterward, not even with database and master-key access. Managed from **Edit Profile → REST API Tokens**; `Api::V1::BaseController` tries the new token table first, then falls back to the legacy column, so no existing integration breaks. A `read_only` token gets `403` on any write action; a repository-scoped token gets `404` on any other repository, the same response an unauthorized user would get.
- **Teams — cross-repository user groups with a lead/member rollup view** (Standard) — closes a real data-model gap flagged twice in planning (CODEOWNERS-style reviewer routing, and again on its own): previously `User`/`RepositoryMember` only supported per-individual, per-repository scoping, with no way to ask "what does my team own that's stuck, across every repo it touches." New `Team` (name, description) has-many-through `TeamMembership` (member/lead role) to `User`, modeled directly on the existing `Repository`/`RepositoryMember` pattern. Admins manage teams and membership under **Settings → Teams** (one member added/re-roled/removed per request, same pattern `RepositoryMembersController` already uses, not a wholesale-replace form — every change is audit-logged). Any team member or lead — no admin access required — gets a `/teams/:id` rollup via a new top-nav **Teams** link: open/stale/needs-response reviews and pending assignments across every member's repositories, plus per-member stats (authored, approvals, comments, last active), extending the existing dashboard and per-user-stats query shapes from a single user to an array of team member IDs. A global admin can open any team's rollup without being a member. License-gated at Standard (`teams`).
- **Pull Request Mode — opt-in live PR/MR review, alongside post-commit** (Extended) — a second, per-repository review lifecycle that runs concurrently with the existing post-commit flow (which is completely unchanged and stays the default); a repository picks either, both, or neither. Scoped to **GitLab and GitHub** for this pass. Reuses `Review`/`Commit` rather than forking into parallel models — a new `review_kind` column (`post_commit`/`pull_request`, default `post_commit` so every existing row is untouched) plus `pr_target_branch`/`pr_head_sha`/`mergeable`/`merged`/`merged_at`, and `source_id` (already used by Upsource import as a generic external-review dedup key) reused as `"<platform>:<repo>#<iid/number>"`. Enable per repository via **Edit → Pull Request Mode** (GitLab/GitHub only), then turn on "Merge request events"/"Pull requests" on that repository's existing webhook — no new webhook URL. New `ProcessPullRequestJob`, fully separate from and never calling into `ProcessPushJob`, handles open/reopen (creates the review and its first commit via the existing `fetch_compare_diff`), synchronize/update (incremental diff as a new `Commit`, redelivery-safe via a `pr_head_sha` check), and close/merge. Symbol indexing, ownership stats, and semantic analysis intentionally fire once, at merge (against the branch the PR actually landed on) rather than on every open/sync — indexing a PR's mutable, force-pushable source branch repeatedly would leave stale entries behind. A new **Merge** button on the review page (`pull_request?` reviews only, gated on every reviewer having approved) calls a new `ReviewsController#merge_pr` action — distinct from the pre-existing `#merge` ("combine several post-commit reviews into one," untouched) — which calls the platform's own native merge endpoint (`Repository#merge_pull_request`, GitLab "Accept MR" / GitHub "Merge PR") rather than Codeveira performing a git-level merge itself. License-gated at Extended (`pr_mode`).
- **Pull Request Mode extended to Gitea and Forgejo** (Extended) — the next lowest-effort platforms after GitLab/GitHub, since `fetch_compare_diff`/`fetch_commit_parent_sha` already worked for `gitea_compatible?` repositories (built for the pre-existing post-commit path); Bitbucket Cloud/Server and Azure DevOps remain unsupported for PR mode since their diff-fetching plumbing doesn't exist yet, and Gerrit is architecturally excluded (its "change" model already collapses push and review into one unit, with no separate open/sync/merge lifecycle to hook into). `Repository#merge_pull_request` gained a `gitea_compatible?` branch calling the platform's native merge endpoint (`POST /api/v1/repos/{owner}/{repo}/pulls/{index}/merge`); `ProcessPullRequestJob` gained a `perform_gitea` handler reusing the exact same `open_pull_request`/`sync_pull_request`/`finalize_pull_request` logic already built for GitLab/GitHub, since Gitea's `pull_request` webhook payload shape mirrors GitHub's (its "new commits pushed" action is spelled `synchronized`, not `synchronize`). Enable per repository via **Edit → Pull Request Mode** (now GitLab/GitHub/Gitea/Forgejo), then turn on "Pull Request" on that repository's existing Gitea/Forgejo webhook.
- **Pull Request Mode extended to Bitbucket Cloud, Bitbucket Server, and Azure DevOps** (Extended) — closes the three-platform gap left by the entry above. All three turned out to genuinely support both "diff between two arbitrary commits" and a native merge endpoint, so the earlier "diff-fetching plumbing doesn't exist yet" note was a build gap, not an architectural blocker like Gerrit's. New `fetch_bitbucket_compare_diff`/`fetch_bitbucket_server_compare_diff`/`fetch_azure_compare_diff` each reuse an existing single-commit diff endpoint's two-revision form and, for Bitbucket Server/Azure, the same JSON-to-diff converter already built for the single-commit case — wired into the same `fetch_compare_diff` dispatch the whole open/synchronize lifecycle already relies on. `Repository#merge_pull_request` gained three new branches: Bitbucket Cloud's `POST .../pullrequests/{id}/merge`; Bitbucket Server's merge, which reads the PR's current `version` first for optimistic-concurrency locking before posting; and Azure's `PATCH .../pullrequests/{id}` with `status: "completed"`. Bitbucket Cloud and Bitbucket Server are the only two platforms whose webhook event type arrives solely via the `X-Event-Key` HTTP header rather than the payload body, so `ProcessPullRequestJob#perform` gained a 4th `event` argument threaded through from the webhook controller just for those two. Azure's webhook has a real quirk worth calling out: there's no distinct "PR closed" event — merged and abandoned both arrive via `git.pullrequest.updated` with a `status` field, and the separate `git.pullrequest.merged` event fires on a merge *attempt* that can still fail, so it's only treated as a confirmed merge when the resource's `status` reads `completed`. Enable per repository via **Edit → Pull Request Mode**, now covering all seven non-Gerrit platforms; turn on the matching PR/pull-request event on that repository's existing webhook config.
- **Pull Request Mode extended to Gerrit, via its native patch-based Change model** (Extended) — closes the last platform gap; what earlier entries called an architectural blocker turned out to be a naming mismatch, not a real one. Gerrit has no PR/MR object, but its Change lifecycle (open → new patch-set → submit/abandon) maps onto the same open/sync/finalize shape the other seven platforms already use — it just needed its own job rather than another `ProcessPullRequestJob` branch. New `review_kind: 'gerrit_change'` (alongside the existing `'pull_request'`) reuses every PR-mode column with no migration; `Review#live_tracked?` (`pull_request? || gerrit_change?`) is the new umbrella predicate the UI/controller gate on instead of `pull_request?` alone. New `ProcessGerritChangeJob`, fully separate from `ProcessPullRequestJob`, dispatches on the Gerrit event `type`: `patchset-created` (patch-set 1 opens, >1 syncs an incremental commit and resets approvals), `change-merged` (finalizes as merged, capturing the event's `newRev` — the actual landed SHA, which can differ from the last patch-set's own revision under Cherry Pick/Rebase Always — into `pr_head_sha`), `change-abandoned` (finalizes as closed), `change-restored` (reopens). New `Repository#submit_gerrit_change` posts a `Code-Review: +2` label then calls Gerrit's own `submit` endpoint, wired as one more branch of the existing `merge_pull_request` dispatch so the Merge button needed no new controller action. One real correctness wrinkle: Gerrit also fires its existing `ref-updated` event when a tracked Change lands, which would otherwise create a second, duplicate review for the same commit alongside the one `ProcessGerritChangeJob` already created — `ProcessPushJob#perform_gerrit` now skips creating a review if a `gerrit_change`-kind review already has that commit as its `pr_head_sha`. Enable per repository via **Edit → Pull Request Mode**, now covering all eight platforms; on Gerrit, configure the `webhooks` plugin (or equivalent) to POST `patchset-created`/`change-merged`/`change-abandoned`/`change-restored` to the existing `/webhooks/gerrit` endpoint.
- **Stacked diffs — auto-linking and auto-rebasing dependent PR stacks** (Enterprise) — an opt-in extension of PR mode for teams that split large changes into a chain of small, dependent pull requests (the Graphite/Sapling workflow) instead of one big one. - **Semantic analysis: typed navigation + diagnostics inlined into the diff** (Enterprise) — the "Phase 2 remainder" typed-navigation and diagnostics-in-diff items every one of the eight language entries above listed as not-yet-built. **Typed navigation:** Find Usages and Go to Declaration now prefer a real, type-resolved `semantic_definitions` match over the tree-sitter index whenever a repository has real semantic analysis enabled and licensed and a match actually exists — falling back to the tree-sitter match otherwise (e.g. PHP, whose engine never returns definitions). No new tables, columns, or env vars; this is entirely new behavior on top of the existing `semantic_definitions`/`semantic_diagnostics` data all eight language drivers already produce.
- **Semantic analysis: per-language dependency-install caching** (Enterprise) — closes the "dependency-install caching" gap every one of the eight language entries above listed as not-yet-built. Every one of the eight `semantic-analysis-*` containers previously did a fully cold install (`go mod download`/`npm ci`/`pip install`/`mvn dependency:resolve`/`composer install`/`dotnet restore`/`bundle install`) on every single `/analyze` request, since the whole workspace — including wherever that install step would normally cache downloads — is a per-request temp directory torn down at the end of the request. Rather than a hand-rolled lockfile-hash-keyed save/restore cache, each container now mounts a persistent named Docker volume at its package manager's own existing content-addressed cache directory (name+version-keyed, or content-hash-keyed for pip), so nothing new has to hash a lockfile, look up a snapshot, or evict anything — the package manager already handles concurrent access to a shared cache dir safely, the same assumption any CI system relies on when reusing a cache dir across parallel jobs. This is also strictly better than a literal lockfile-hash cache: it's reused across every repository analyzed for that language, not just repeat runs of the identical repo. Ruby is the one real behavior change rather than a pure mount: gems previously installed into `vendor/bundle` inside the ephemeral per-request workspace by design (to avoid writing into a shared path the container user might not own); they now install to a persistent `/home/analyzer/.cache/bundle`, owned by the same non-root `analyzer` user every other language's cache dir already uses, so that original concern no longer applies. No new env vars or `.env.example` changes — cache paths are internal container details, same as the pre-existing `GOPATH`/`NPM_CONFIG_CACHE`/`PIP_CACHE_DIR`. Trust boundary unchanged: the cache only ever holds package content that already passed through that language's existing egress-allowlist proxy under the same install flags as before, never target-repo source; the new, real limitation is that these volumes have no automatic eviction or size cap and grow unboundedly like any CI package cache — clear one manually with `docker volume rm` if disk usage becomes a concern.

- **Ownership-Based Risk Scoring, with an optional merge-block gate** (Standard) — reuses the `file_ownership_stats` git-history index built for reviewer suggestions to flag reviews where the author has little or no prior history with the files they're changing: every review page shows a **RISK** badge (gray/amber/red) giving the percentage of the review's changed files the author has never previously committed to in this repository. A repository can optionally set a **merge-block threshold** (Edit page, 1–100, blank = disabled); once a review's risk score reaches it, approving, closing, or merging (including PR mode/Gerrit) is blocked with an explanation banner until a global admin overrides it. Enforced identically on the web UI and the REST API via a new shared `RiskGateEnforceable` concern, the same dual-controller pattern already used for the Checklist enforcement gate, so the policy can't be bypassed by using one surface instead of the other.
- **Automatic key-based post-commit review accumulation, on customer request** (Free) — closes the real gap in a strictly post-commit, no-PR/MR workflow: a manual version of "add later commits to an existing review" already shipped (`ReviewsController#add_commits`, the "Add commit(s)" modal on the review page), but a fresh push always opened a brand-new review even when it was really a follow-up to one already open. Every push handler (`ProcessPushJob`, all 7 sources — GitLab/GitHub/Gitea+Forgejo/Bitbucket Cloud/Bitbucket Server/Azure DevOps/Gerrit) now checks, before creating a review, whether the incoming push's commit messages (or branch name) carry a ticket key — same extraction `Repository#issue_keys_for` already used outbound for task-tracker sync, refactored into a new `issue_keys_in_text` so it can scan raw commit text too — matching one already present on an already-`open`, ordinary post-commit review. Live-tracked PR-mode/Gerrit-mode reviews are never matched into by this (they're already synced by their own dedicated job via `source_id`), and Gerrit's existing dedup guard against its own `ref-updated`/`change-merged` double-fire runs first, unaffected. A migrated-in Upsource review keeps accumulating the same way once imported, since it's just an ordinary open post-commit review at that point.

- **Migration Safety Analyzer** (Standard) — flags risky Rails migration patterns in newly-added `db/migrate/*.rb` files on every push: a NOT NULL column added without a default, a non-concurrent index build, a column/table rename or remove, and type changes. Posts each as an inline review comment from a dedicated `migration-safety-bot` account, the same posting/dedupe mechanism Architectural Lint and Duplicate Code Detection already use. Off by default, toggled per instance under **Settings → Migration Safety**. License-gated at `migration_safety: 'standard'`, the same tier as Architectural Lint/Duplicate Detection.
- **Per-repository AI suggestion suppression / learning** (Extended) — every AI finding now carries a free-form `category` tag, and any AI bot comment can be marked 👎 **Not helpful** directly on the diff (`Comment#dismissed`). Category tagging and dismissal are recorded on every license tier — only the suppression effect on future reviews is gated at `ai_learning: 'extended'`.
- **Secret Scanning** (Standard) — scans every `added` diff line on every push for hardcoded credentials, no external tool or CI configuration required — the automatic, always-on counterpart to SAST Findings above (which just ingests output from a scanner someone runs and configures themselves). Six vendor-specific regexes fire on any match (AWS Access Key ID, GitHub token, Slack token, Google API key, Stripe live secret key, PEM private key block); a seventh generic `password/secret/api_key/token = "..."` pattern is additionally gated by Shannon entropy (≥3.0) plus placeholder-word and Ruby-interpolation exclusions, since an unconditional string-literal-assignment match on its own would be far too noisy. The matched value is masked in the posted comment (first/last 4 characters kept, the rest replaced with `•`) before posting from a dedicated `secret-scanning-bot` account — same posting/dedupe mechanism Architectural Lint, Duplicate Code Detection, and Migration Safety Analyzer already use. New general-purpose diff line-number reconstruction (`SecretScanner#each_added_line`, advancing on both `added` and `context` lines, never on `removed`) — the existing `MigrationSafetyAnalyzer#build_source` line-counter only works for brand-new files (100% `added` lines) and couldn't be reused as-is for arbitrary modified files. Off by default, toggled per instance under **Settings → Secret Scanning**. License-gated at `secret_scanning: 'standard'`, the same tier as the other three diff-scanning bots.
- **Semantic Duplicate Detection** (Standard) — complements Duplicate Code Detection above: fingerprint matching only catches near-exact/copy-paste duplicates, this catches two *differently-written* implementations of the same problem by reusing the `SymbolDefinition#embedding` + cosine-similarity infrastructure already built for Semantic Search, rather than a second embedding call. For every embedded, fingerprinted definition touched by a push, `SemanticDuplicateDetector` finds the highest-similarity match elsewhere in the same repository/branch — excluding any candidate sharing the same fingerprint, since Duplicate Code Detection already flags that pair — and posts an inline comment from a dedicated `semantic-duplicate-bot` account when the score clears a 0.87 cosine-similarity threshold, deliberately higher than Semantic Search's own 0.5 manual-search threshold since this is an unprompted automated comment rather than a ranked suggestion list. Runs at the end of `GenerateCodeEmbeddingsJob`, not inside `IndexSymbolsJob` like the other three diff-scanning bots — embeddings for a review's own touched files don't exist yet at the point `IndexSymbolsJob` runs its synchronous checks, since `GenerateCodeEmbeddingsJob` is only enqueued at the very end of that job and fills them in asynchronously afterward. No new license key: double-gated on the existing `duplicate_detection` and `semantic_search` features (both already `'standard'`). Off by default, toggled as a second toggle on the existing **Settings → Semantic Search** page rather than a new page, since it depends on that page's already-configured embedding provider.
- **CI Flakiness Detection** (Enterprise) — when a `/webhooks/ci` status update reports a failure, `CiFlakinessDetector` checks whether that same pipeline has also failed recently on other reviews in the repository that touched none of the same files (last 20 runs of that pipeline, scoped to the repository); at 3 or more such unrelated failures, posts a general (non-inline) comment from a dedicated `ci-flakiness-bot` account flagging the failure as possibly flaky, so a reviewer doesn't chase a bug that isn't in the current diff. No new table: every CI status update already gets its own row per review, so recent per-pipeline history for a repository was already there, unread, before this. No new license key (reuses `ci_status: 'enterprise'`) and no new toggle — configuring the CI status webhook is already the opt-in, the same pattern SAST Findings and Code Coverage already follow.
- **Dead Symbol Detection** (Standard) — `DeadSymbolDetector`, wired into `IndexSymbolsJob` alongside the other three diff-scanning bots, flags a newly added function/method with zero `SymbolReference` rows anywhere else in the repository+branch, reusing the exact lookup that already backs the Find Usages UI feature. Scoped to `kind in [function, method]` (the kinds that generate a `reference.call` tag when used) and to definitions whose line actually falls inside this diff's added lines, so a pre-existing unreferenced method isn't re-flagged every time its file is touched by something unrelated. - **Semantic analysis: self-hosted VCS reachability for the PHP Composer proxy, closing the last "Phase 2 neutral gap"** (Enterprise) — `semantic-analysis-php-proxy`'s allow-list was a bake-time-static `filter.conf`, so a self-hosted GitLab/Gitea/Forgejo/Bitbucket Server instance at an admin-configured hostname could never be reached, no matter how it was configured — logged as the sole remaining gap in the three prior Semantic analysis entries above. Fixed with a dynamic, per-repository opt-in allow-list rather than a bigger proxy redesign: a new `composer_proxy_self_hosted_allowed` boolean on `Repository` (default off — zero behavior change for anyone who doesn't opt in), and a new `ComposerProxyFilter` service that recomputes the full allow-list from scratch from the `repositories` table (base 8 public hosts plus every opted-in repo's `gitlab_url` host, for `source in [gitlab, gitea, forgejo, bitbucket_server]` only) and writes it to a new shared Docker volume (`php_composer_proxy_filter`, mounted into both `app` and `semantic-analysis-php-proxy`) — an `after_commit`/`after_destroy_commit` on `Repository` enqueues `RegenerateComposerProxyFilterJob` (Sidekiq) whenever `composer_proxy_self_hosted_allowed`, `gitlab_url`, or `source` changes, and the proxy's new `entrypoint.sh` sends tinyproxy a `SIGHUP` every ~30s to re-read the file without dropping connections — no new listening port or Docker-socket access needed. Every host is `Regexp.escape`d before being written (so a hostname's dots can't act as an ERE wildcard) and re-checked against `SsrfGuard` as defense-in-depth, even though `gitlab_url` is already SSRF-validated at save time. Gated at the existing `semantic_analysis: 'enterprise'` license key, exposed as a checkbox on the repository Edit page next to the existing semantic-analysis settings. Caught a real bug during test-driven development, not just a test artifact: the initial `after_commit`/`after_destroy_commit` implementation both pointed at a method named `regenerate_composer_proxy_filter`, and Rails' `set_callback` silently replaces rather than appends a second callback registration with the same filter name + kind — so repository create/update silently stopped enqueuing the regeneration job entirely, leaving only the destroy path working; fixed by giving the two callbacks distinct method names.

- **Redis 7 → Valkey 9** — switched the `redis` service (and the optional `docker-compose.sentinel.yml` overlay) from `redis:7-alpine` to `valkey/valkey:9-alpine`. Valkey is a BSD-3-Clause, Linux Foundation–maintained fork of Redis, adopted to keep this project clear of Redis 8's AGPL/RSAL tri-license terms for a commercially-sold product. Valkey is wire-protocol compatible with Redis — Sidekiq, ActionCable, and `lib/redis_sentinel_config.rb` needed zero code changes, and the Sentinel HA overlay (image tags, `valkey-server`/`valkey-cli` binary names) worked identically after the swap. **This is not a trivial drop-in for an install with existing data — action required on upgrade:**
  - Redis 7.4+ (which is what `redis:7-alpine` has resolved to for a while) writes RDB snapshots in on-disk format version 12 (added for hash-field-TTL support, applied to every dump regardless of whether that feature is used). Valkey 9.1.1's RDB loader hard-rejects any header version newer than it knows, failing outright with `Can't handle RDB format version 12` before parsing a single key — and `DUMP`/`RESTORE`/`MIGRATE` fail the identical way, since `DUMP`'s payload footer carries the same version marker. Simply pulling the new image against an existing `./redis/dump.rdb` will crash-loop the container.
  - Migrate live, over the RESP protocol, instead of relying on the RDB file:
    1. Preserve the old file rather than deleting it, then let Valkey start clean: `docker compose run --rm --entrypoint sh redis -c "mv /data/dump.rdb /data/dump.rdb.redis7.bak"` then `docker compose up -d redis`
    2. Start a throwaway `redis:7-alpine` container read-only against the same `./redis` bind mount (on the app's Docker network) and copy every key across by type (`GET`/`SET`, `LRANGE`/`RPUSH`, `SMEMBERS`/`SADD`, `ZRANGE ... WITHSCORES`/`ZADD`, `HGETALL`/`HSET`, preserving remaining `TTL`) — e.g. via `docker compose exec app bin/rails runner` using the `redis` gem already in the bundle
    3. Confirm `DBSIZE` matches on both ends before discarding the old container; keep `dump.rdb.redis7.bak` until you're confident the copy is complete — see "Redis → Valkey migration" in `documentation.md` for the full walkthrough

  Nothing to do on a fresh install — `./redis` is created empty and initialized normally on first boot under Valkey 9.
